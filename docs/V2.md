# Aziry Tech WhatsApp AI Sales Agent — Version 2 (Meta WhatsApp Cloud API)

Branch: `feature/v2-meta-whatsapp-cloud-api`

V2 adds the official Meta WhatsApp Cloud API next to the existing Baileys (QR) integration.
Each merchant uses exactly one of them. The AI engine, products, orders, special requests,
insights and billing are unchanged and shared by both.

---

## 1. Architecture

```
Customer ─► Meta Cloud API ─► POST /webhooks/whatsapp
                                 │ verify X-Hub-Signature-256 (HMAC-SHA256, raw body)
                                 │ store events (dedupe key)  ──► 200 OK immediately
                                 ▼
                     whatsapp_webhook_events  (Postgres queue)
                                 │ webhookWorker (in-process every 5 s + cPanel cron every minute)
                                 ▼
          tenantResolver (metadata.phone_number_id ─► merchant)   ◄── only source of merchantId
                                 ▼
          messageProcessingService  (provider-independent)
            dedupe ─► 24h window ─► read/typing ─► voice STT ─► STOP/START
            ─► personal / bot off / suspended ─► AI engine (agent.js, tools, fallback)
            ─► takeover re-check ─► Cloud API send ─► save wamid + status
                                 ▼
          statusHandler: sent ─► delivered ─► read / failed (monotonic, tenant-checked)
```

Outbound messages from anywhere in the app (order updates, special requests, re-engagement, OTP,
manual replies) go through `src/whatsapp/sender.js` → `integrations/whatsapp/messageSender.js`, which:

- picks the merchant's transport (Cloud API if connected, otherwise Baileys if `FEATURE_BAILEYS=true`);
- sends free-form text only inside the 24-hour customer service window;
- outside the window, uses the merchant's **approved** template for that purpose, or refuses;
- refuses marketing to opted-out customers, and marketing templates without explicit opt-in.

## 2. Environment variables

All values are placeholders in `.env.example`. **Never commit real values.**

| Variable | Required | Notes |
|---|---|---|
| `FEATURE_CLOUD_API` | – | `true` enables the webhook and worker. Default `false`. |
| `FEATURE_EMBEDDED_SIGNUP` | – | `true` only after Meta approval. Default `false`. |
| `FEATURE_BAILEYS` | – | Legacy QR. Default `true`. Set `false` after all merchants migrate. |
| `WEBHOOK_WORKER_IN_PROCESS` | – | Default `true`. Set `false` to rely on the cron job only. |
| `META_APP_ID` | Cloud API | Meta app → Settings → Basic |
| `META_APP_SECRET` | Cloud API | Used to verify webhook signatures. Without it every webhook is refused (503). |
| `META_WEBHOOK_VERIFY_TOKEN` | Cloud API | Any long random string; same value in Meta webhook settings |
| `META_GRAPH_API_VERSION` | – | Default `v23.0`. Check Meta's changelog and update deliberately. |
| `META_EMBEDDED_SIGNUP_CONFIG_ID` | Signup | From Meta → WhatsApp → Embedded Signup configuration |
| `TOKEN_ENCRYPTION_KEY` | Cloud API | 32 bytes, base64. Encrypts Meta tokens. **Back it up** — tokens are unreadable without it. |
| `TOKEN_ENCRYPTION_KEY_PREVIOUS` | – | Only while rotating keys |
| `DATA_ENCRYPTION_KEY` | – | Optional 32-byte key for messages; otherwise derived from `ENCRYPTION_KEY` |
| `APP_URL` | – | Public HTTPS URL of the app |
| `TRUST_PROXY` | cPanel | `1` behind Apache/Passenger so rate limits see real client IPs |
| `AZAMPAY_CALLBACK_SECRET` | Billing | Put `https://<domain>/api/billing/webhook?key=<secret>` in the AzamPay dashboard |
| `BACKUP_DIR` | – | Session backups, outside the project. Default `~/aziry-backups` |

Generate keys: `node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"`

## 3. Database migration

The project previously used `prisma db push`, and `prisma/migrations` was a stale SQLite history
(now in `prisma/legacy-sqlite-migrations/`). V2 introduces proper migrations:

- `0_baseline` — the schema exactly as it is in production before V2 (nothing to run).
- `20261110000000_v2_whatsapp_cloud_api` — **additive only**: 8 new tables, new nullable/defaulted
  columns on `merchants`, `conversations`, `messages`, plus a data backfill (`UPDATE` only):
  `needsHuman` conversations get `handoverState = 'HUMAN_REQUESTED'`, and `customerWaId` is filled
  from `…@s.whatsapp.net` numbers. No table, column or row is dropped or deleted.

**Production steps (take a Supabase backup first):**

```bash
# 1. Confirm production matches the baseline (must print nothing / exit 0)
npx prisma migrate diff --from-url "$DATABASE_URL" \
  --to-schema-datamodel <(git show 23a5fb4:prisma/schema.prisma) --exit-code

# 2. Record the baseline as already applied (runs no SQL)
npx prisma migrate resolve --applied 0_baseline

# 3. Apply V2
npx prisma migrate deploy
npx prisma generate
```

If step 1 reports differences, stop: production has drifted from the code and the baseline must be
regenerated from production (`prisma migrate diff --from-empty --to-url`).

The whole sequence was rehearsed on a local PostgreSQL 18 copy with V1 data, including under
non-UTC server time zones.

## 4. Deploying on cPanel

1. **Node.js app** (cPanel → *Setup Node.js App*): Node 18+, application root = repo folder,
   startup file `src/index.js`. Add the environment variables in that screen.
2. Install and migrate (cPanel terminal, after `source <nodevenv>/bin/activate`):
   `npm ci && npx prisma generate && <migration steps above>`.
3. **HTTPS is required** by Meta. Webhook URL: `https://<domain>/webhooks/whatsapp`.
4. **Cron job** (cPanel → Cron Jobs, every minute) — Passenger can put an idle app to sleep,
   and the cron drains the queue and retries regardless:
   ```
   * * * * * cd ~/<app> && ~/nodevenv/<app>/<ver>/bin/node scripts/drain-webhook-queue.js >> ~/logs/aziry-webhook.log 2>&1
   ```
   Processing is safe with both the in-process worker and cron running (`FOR UPDATE SKIP LOCKED`).
5. Set `TRUST_PROXY=1`.
6. Restart the app from cPanel after every deploy.

Baileys sessions keep running for merchants not on the Cloud API. On shared hosting they
disconnect whenever Passenger idles the process — another reason to migrate merchants.

## 6. Migrating a merchant from Baileys to the Cloud API

1. Decide per number: **Coexistence** (keep using the WhatsApp Business app; availability varies by
   country) or **move fully** (remove the number from the app; chat history on the phone is lost).
2. Connect the number (Embedded Signup, or manually during the pilot). Connecting automatically stops
   the merchant's Baileys session, and Baileys refuses to start again while a Cloud connection exists.
3. Existing conversations continue: Cloud API conversations use the same `…@s.whatsapp.net` key.
   Old `@lid` conversations have no phone number and start fresh.
4. After all merchants are migrated and confirmed: `FEATURE_BAILEYS=false`, then remove Baileys code.

## 7. Rollback

- **Fast (no deploy):** `FEATURE_CLOUD_API=false` and restart. The webhook returns 404; Meta retries
  deliveries for a limited time, so re-enable quickly or point affected merchants back to Baileys.
  Disconnect the merchant's Cloud connection so Baileys may start again.
- **Code:** redeploy `main`. The V2 migration is additive, so V1 code runs on the migrated database.
  Messages written by V2 use the `v2:` (AES-GCM) format; `main` must include the V2 `crypto.js`
  (backported on `fix/number-safety-queue`) or those messages show as unreadable.
- **Database:** do not roll back the migration; the extra tables and columns are harmless to V1.

## 9. Security findings and fixes

| Finding | Fix |
|---|---|
| WhatsApp `creds.json` committed in `backups/` of a public repo | Untracked, ignored, backups moved outside the project. **History still contains it — log out linked devices; history rewrite pending owner approval.** |
| AzamPay webhook unreachable (401) and forgeable if exposed | Mounted before the auth router, callback secret, random reference, amount check |
| Upload stored XSS (`evil.html` as `image/png`) | Extension from verified MIME type |
| AES-CBC without integrity; silent plaintext fallback | AES-256-GCM, fixed 16-byte tag, throws on failure; V1 data still readable |
| Suspended merchants kept access for 7 days | Status checked per request (30 s cache, invalidated on suspend) |
| Tests could hit production via `.env` override | `.env` doesn't override in tests; DB client refuses non-localhost in test mode |
| Webhook security (V2) | Signature on raw body, constant-time compare, dedupe, tenant only from `phone_number_id` |
| Template webhooks could touch other tenants | Scoped to the sending WABA |
| Marketing without consent via utility template | Opt-in required for marketing by message kind and category; purpose ↔ category enforced |
| Bot on/off stored in memory | Stored in the database |

Still open: CORS allows `*`; CSP disabled in helmet; `aiUsage` never resets monthly automatically;
dashboard static labels don't follow the saved language until it is toggled; voice STT uses the
retired `gemini-1.5-flash` model.
